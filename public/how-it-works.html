How Vulnder works

Vulnder collects vulnerability data every hour. On each request it turns your input into stack items, matches them to CVEs and ranks the results.

The pipeline

Every hour: collect

  1. Fetch

    Hourly: CVE records with CISA's Vulnrichment assessments, GitHub advisories (packages and fixed versions) and CISA KEV. Daily: FIRST's EPSS scores, end-of-life dates, and the Metasploit and Nuclei indexes. Also hourly: write-ups from Huntress, Rapid7, watchTowr, CERT-EU and NCSC UK, read from their RSS feeds.

  2. Merge and record changes

    One record per vulnerability. New CVEs, KEV additions, EPSS jumps and released fixes become events for What changed and the Atom feed.

  3. Group similar CVEs AI

    Each new CVE title is embedded once, so near-duplicates within a product can be grouped. The model sees CVE text only; code sets the threshold.

  4. Retain

    CVEs published or changed in the last 90 days, so an old CVE added to KEV today, or newly reported by CISA as actively exploited, still shows. A CVE CISA reports exploited, or one likely to be exploited, is kept and shown for a year at any severity. CVSS 7.0+ CVEs are kept for a year too, but show only inside the window you pick. A slim index of every CVE ID ranks pasted CVE lists of any age.

When you ask: match and rank

  1. Screen AI

    Text that reads like instructions to an AI is refused: first by a phrase check, then by Jev, TypeSafe's decision model.

  2. Extract names AI

    A model lists the components you named. Code drops any name that isn't in your text, whether invented or planted.

  3. Resolve

    Names become catalog products. A broad name like "Cisco switches" becomes several close matches, marked ?. Lockfiles and SBOMs start here, parsed in your browser. CVE lists go straight to Match.

  4. Judge fit and teams AI

    If your scale or hosting is clear, Jev rates each close match, so a home lab sees small-business gear first. For enterprise stacks it also names the team that owns each component. Code decides what to do with its answers.

  5. Match

    Stack items are matched to CVEs in D1. OSV checks whether an exact package version is affected.

  6. Rank

    Each result gets a priority, an ordering score, its reasons and a time to respond. Fix first orders components by what upgrading each one removes.

Where AI is used

Models read text and make judgement calls. Code decides what you see, because a rule can be tested and a model's ranking can't.

Used forScreening your text, extracting component names, judging close-match fit and team ownership, grouping similar CVE titles.
Never used forRanking CVEs, setting a priority, hiding a match, reading your lockfile.
OutputTreated as untrusted and checked against a schema and your own words. Fit only reorders close matches; it never removes one.

How results are ranked

Priorities follow CISA's SSVC decisions, from its Vulnrichment assessments on CVE records. Evidence of exploitation outranks prediction (EPSS, NIST LEV), which outranks severity (CVSS). A low CVSS never holds the first two back: attackers chain lower-severity bugs into serious attacks.

  • Act now: in CISA's KEV catalog or reported by CISA as actively exploited, at any severity, within 24 hours. Before exploitation is seen: EPSS 50%+, a critical bug with EPSS 10%+ or NIST LEV 20%+, an edge device (VPN, firewall, gateway) an attacker can take over automatically, or a critical bug trusted security teams are warning about (see Written up, below), within 3 days. Exploited CVEs come first.
  • Attend: EPSS 10%+ or NIST LEV 20%+ at any severity, a similar CVE in the product exploited, a Metasploit exploit module, CVSS 9.0+, public exploit code for a bug that is automatable or gives full control, an edge-device bug that is automatable or gives full control, or CVSS 8.0+ public for 60 days. Within 7 days.
  • Watch: CVSS 8.0+, a proof-of-concept or other public exploit code, rated automatable by CISA (or a Nuclei scanner template where CISA hasn't rated it), any bug CISA has assessed on an edge device, or CVSS 7.0+ public for 60 days. Within 30 days.
  • Track: affects your stack and nothing above applies. Next routine update.
ScoreA 0–100 heuristic that orders results within a priority, from threat, impact, reachability and ransomware use. Not a probability.
Older CVEsCVEs from the last year that CISA reports exploited or that are likely to be exploited (EPSS 10%+ or NIST LEV 20%+), at any severity, and CVSS 9.9+ CVEs show whatever window you pick.
OverdueA high-severity CVE still unfixed 60 days after publication moves up one priority. It never changes the score or reaches Act now.
Edge devicesTreated as internet-facing, ranked ahead of similar results, and given CISA BOD 26-04 deadlines, which can raise a priority but never lower one. VPNs, firewalls and gateways are ticked by default; change them under Edit stack.
Out of supportSoftware past its vendor's end of support ranks with Act now; support ending within 90 days ranks with Attend. This is a finding on the component and doesn't change its CVEs' priorities.
Targeted by attackersAn item with any CVE CISA added to KEV in the last 90 days gets a notice, whatever version those CVEs affect. In 2025–26, about a third of products with a KEV add got another within 90 days, so patch its next advisory within days. Like out of support, it doesn't change any CVE's priority.
Written upEvery hour Vulnder reads the RSS feeds of Huntress, Rapid7, watchTowr, CERT-EU and NCSC UK for the CVEs they name. A critical CVE (CVSS 9.0+) that two of them write up, or that one calls critical or urgent, goes to Act now for 30 days, whatever its EPSS: EPSS and CISA's assessment take days to catch up with a new CVE. Any write-up ranks a result ahead of similar ones, and the result links to it. A write-up isn't evidence of exploitation, even when it says so: only CISA KEV and CISA's own reports are.
ReasonsEach result names what decided it and what data is missing. A result with little data reads as unknown, not safe.

Response times are guidance, not deadlines. Full rules: RANKING.md.

Use it with an AI assistant

Vulnder runs an MCP server, so a coding agent or chat assistant can rank CVEs for you while it works. There's no account or key to set up.

  1. Connect your AI agent to Vulnder

    Add the server https://vulnder.com/mcp in whichever tool you use.

    In Claude Desktop or claude.ai, open Settings, then Connectors, choose Add custom connector and paste the same address.

  2. Ask it

    The agent gets two tools: rank_stack for packages and products, and rank_cves for a list of CVE IDs. Try:

    • "Use Vulnder to rank the CVEs affecting this repo's lockfile, and fix the Act now ones."
    • "We run FortiGate firewalls, Exchange Server SE and Postgres 16. What should we patch first?"
    • "Rank the CVEs in this Trivy report with Vulnder."

    Answers come with the same priorities, reasons and Fix first list as this site, and a link to the full results page.

  3. Check your agent's own MCP servers

    MCP servers are software too, with CVEs of their own. Drop your .mcp.json, mcp.json or claude_desktop_config.json on the home page. Vulnder reads the servers it starts with npx, uvx or docker, in your browser, and sends only their package names and versions. It never reads env or headers, where your keys live. Servers that run local code or sit at a remote URL are listed as not checked.

Agents have a rate limit of their own: new lookups are limited per address, and repeat lookups are free. Connectors in claude.ai and other hosted assistants call from the provider's servers, so their users share that limit. If you hit it, connect from a local agent such as Claude Code, or run your own copy.

Privacy

  • Only free-text entries describing your stack are logged, by Cloudflare's AI Gateway in the account that runs this site. They go to Cloudflare Workers AI to pick out component names.
  • Vulnder doesn't store your stack or what you type. Parses are cached under a hash of the text, never the text.
  • Lockfiles, SBOMs and MCP configs are read in your browser and never reach the model or Vulnder's storage. Only package names and versions are sent; an MCP config's env and headers, where keys live, aren't read at all.
  • MCP requests from AI agents aren't logged or stored, and the MCP server calls no model.
  • CVE lists and scan reports are read in your browser too, and aren't stored. Only the CVE IDs go into the stack link; host names, addresses and the rest of the report stay on your machine.
  • Stack links are kept out of logs, and pages send no Referer, so advisory links don't leak your stack.
  • IP addresses are only rate-limit keys, or a hash salted afresh each day.
  • No analytics or tracking. Cloudflare Turnstile protects the submit form.
  • Cloudflare processes every request, stack links included. If that's too much, run your own copy.

Limits

No scanningVulnder knows only what you give it. A lockfile gives exact versions; a description gives matches to confirm.
Time windowStack results cover the last 7, 30 (default) or 90 days, plus the older CVEs above. A pasted CVE list is ranked whatever its age.
CoveragePackages from npm, PyPI, Maven, Go, Cargo, NuGet, Composer, RubyGems, Hex and pub, and products named in CVE records. Anything else shows as unrecognised. In an MCP config, only servers started from a package or container image can be checked.
New CVEsMany arrive without a score. Results show which data is missing.
