How Vulnder works

Every hour, Vulnder collects what's known about new vulnerabilities. When you ask, it works out what you run and ranks the matches by what to fix first.

The pipeline

Every hour: collect

  1. Fetch

    CVE records with CISA's exploitation assessments, GitHub advisories for packages and fixed versions, CISA's KEV catalog and FIRST's EPSS scores.

  2. Merge and record what changed

    One record per vulnerability. New issues, KEV additions, EPSS jumps and fixes become events for "What changed" and the Atom feed.

  3. Group similar CVEs AI

    Each new CVE title is embedded once, so near-duplicates in a product can be grouped. The model sees CVE text only; code sets the threshold.

  4. Keep 90 days

    Anything published or changed in the last 90 days, so an old CVE that lands on KEV today still shows.

When you ask: match and rank

  1. Screen AI

    Text that reads like instructions to an AI is refused, first by a phrase check, then by Jev, TypeSafe's decision model.

  2. Pick out components AI

    A model lists the components you named. Any name that isn't in your own words is dropped, whether made up or planted.

  3. Resolve

    Names become catalog products. A vague one like "Cisco switches" becomes several close matches, marked ?. Lockfiles and SBOMs start here, read in your browser.

  4. Judge fit and teams AI

    If your scale or hosting is clear, Jev rates each close match, so a home lab sees small-business gear first. For enterprise stacks it also names the team that owns each component. Code acts on its answers.

  5. Match

    Your stack meets the vulnerability data. OSV checks whether an exact package version is affected.

  6. Rank

    Each result gets a priority, an ordering score, its reasons and a time to respond. Fix first orders components by what upgrading each one removes.

Where AI is used, and where it isn't

AI reads and judges; code decides. A rule can be read, tested and argued with. A model's ranking can't.

  • Models do: screen your text, pick out component names, judge close-match fit and enterprise teams, and group similar CVE titles.
  • Models never: rank CVEs, set a priority, hide a match, or see your lockfile.
  • Their answers are untrusted. Output is checked against a schema and your own words. Fit only reorders close matches, never removes one.
  • They fail open. If a model is down, parsing carries on without it.

How results are ranked

Priorities follow CISA's SSVC decisions. Evidence of exploitation outranks prediction, which outranks severity (why that matters more now).

  • Act now: on CISA's KEV catalog or actively exploited, within 24 hours. Before exploitation is seen: EPSS 50%+, a critical bug with EPSS 10%+, or an edge device (VPN, firewall, gateway) an attacker can take over automatically, within 3 days. Exploited bugs come first.
  • Attend: likely or critical. EPSS 10%+, NIST LEV 20%+, a similar CVE in the product exploited, CVSS 9.0+, or an edge-device bug that is automatable or gives full control. Within 7 days.
  • Watch: CVSS 8.0+, a proof-of-concept exploit, or rated automatable by CISA. Within 30 days.
  • Track: affects your stack, nothing above applies. Next routine update.
  • Score. A 0–100 heuristic orders results within a priority, from threat, impact, reachability and ransomware use. It isn't a probability.
  • Older. Known-exploited, likely-exploited and CVSS 9.9+ CVEs from the last year always show, whatever window you pick.
  • Edge devices. Treated as internet-facing, ranked ahead of similar results, and given CISA's BOD 26-04 deadlines, which can raise a priority but never lower one. VPNs, firewalls and gateways are ticked for you; change any under Edit stack.
  • Reasons. Each result names what decided it and what data is missing, so a quiet result reads as unknown, not safe.

Response times are guidance, not deadlines. Full rules are in the README.

Use it with an AI assistant

  • Export for AI on the results page saves a Markdown brief for an assistant or coding agent: check each finding, fix or mitigate it, report one outcome per CVE. It marks advisory text as quoted data, never instructions, so a planted line can't steer your agent.
  • The JSON feed at /api/feed?s=… carries the same priorities, scores, reasons and Fix first list.
  • The Atom feed gets one entry per change; the badge counts known-exploited CVEs for a README.
  • For agents, llms.txt describes the feeds and the stack link format, so an agent can build and fetch a stack itself.

Pasting an export into a hosted AI shares your stack with that provider, and a list of what you run is useful to attackers. Check their data policy first.

Privacy

  • Your stack and text are never stored or logged. Parses are cached under a hash, never the text.
  • Free text goes to Cloudflare Workers AI. Its AI Gateway can log those requests, text included, in the account that runs the site.
  • Lockfiles and SBOMs are read in your browser and never reach the model. Only package names and versions are sent.
  • Stack links are kept out of logs, and pages send no Referer, so advisory links don't leak your stack.
  • IP addresses are only rate-limit keys, or a hash salted afresh each day.
  • No analytics or tracking. Cloudflare Turnstile protects the submit form.
  • Cloudflare processes every request, stack links included. If that's too much, run your own copy.

What it doesn't do

  • It doesn't scan your systems. It knows what you tell it. A lockfile gives exact versions; a sentence gives matches to confirm.
  • It covers recent CVEs. 30 days by default, up to 90, not every old bug you carry.
  • It knows what the data names. Packages from npm, PyPI, Maven, Go, Cargo, NuGet, Composer, RubyGems, Hex and pub, and products in CVE records. Anything else shows as unrecognised.
  • New CVEs are thin. Many arrive unscored. Results say so rather than guess.
